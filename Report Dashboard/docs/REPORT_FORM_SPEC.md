# REPORT_FORM_SPEC.md — مشخصات فنی فرم گزارش استاندارد

> **هدف این فایل:** نسخه فنی برای تیم BPMS — تعریف فیلد‌به‌فیلد پنج بخش فرم گزارش دوره‌ای واحد، نوع داده، الزامی/اختیاری، قواعد اعتبارسنجی، و فهرست بسته دسته‌بندی موانع/ریسک. مسیر بحرانی پروژه طبق بخش ۴.۲ سند اجرایی.

**نسخه:** 1.0 — پیشنهادی  
**وضعیت:** **[پیشنهادی — نیازمند تأیید]** — باید توسط معاونت برنامه‌ریزی و تیم BPMS مصوب شود  
**فایل همراه:** [`REPORT_FORM_SPEC_ONEPAGER.md`](./REPORT_FORM_SPEC_ONEPAGER.md) — نسخه یک‌صفحه‌ای برای جلسه مصوبه  
**پیش‌نیاز:** این فرم فرض می‌گیرد BPMS توانایی تعریف فیلد ساختارمند را دارد. اگر این توانایی محدود است، مسیر جایگزین در `ASSUMPTIONS.md` ثبت شده (فرم موازی سبک خارج از BPMS).

## قانون اصلی فرم

> **هیچ عددی که قرار است در داشبورد دیده شود، اجازه ندارد فقط داخل متن آزاد باشد.**
> اگر عددی مهم است، فیلد اختصاصی دارد.

این قانون در هنگام طراحی فرم در BPMS یا هر جایگزین آن باید به‌صورت صریح در راهنمای تکمیل برای واحدها بیاید.

## ساختار کلی فرم

فرم گزارش دوره‌ای از پنج بخش تشکیل می‌شود. هر بخش به یک مقصد متفاوت می‌رود:

| بخش | نام | نوع ورودی | مقصد داده |
|---|---|---|---|
| ۱ | شاخص‌های کمی | فیلد ساختارمند | انبار داده — محصول B |
| ۲ | وضعیت پروژه‌ها و اقدامات | انتخاب از فهرست + درصد | انبار داده — محصول B |
| ۳ | موانع و ریسک‌ها | انتخاب دسته + متن | هر دو محصول |
| ۴ | روایت و تحلیل واحد | متن آزاد | مغز دوم — محصول A |
| ۵ | پیوست‌ها | آپلود فایل | Object Storage → ingestion محصول A |

## بخش ۱ — شاخص‌های کمی

هر ردیف از این بخش یک مقدار شاخص در این دوره است.

### فیلدهای هر ردیف شاخص

| نام فیلد | نوع داده | الزامی | اعتبارسنجی | توضیح |
|---|---|---|---|---|
| `indicator_id` | string | ✓ | باید از فهرست مصوب `dim_indicator` انتخاب شود | شناسه شاخص، مثلاً `IND-HQ-0014` |
| `value_actual` | decimal(18,4) | ✓ | عدد واقعی؛ منفی مجاز است اگر شاخص اجازه دارد | مقدار واقعی دوره جاری |
| `value_target` | decimal(18,4) | اختیاری | — | هدف این دوره؛ اگر خالی، از `dim_indicator.default_target` گرفته می‌شود |
| `unit_of_measure` | string | ✓ | باید با `dim_indicator.unit_of_measure` تطابق داشته باشد | واحد سنجش (عدد، درصد، میلیون ریال، ...) |
| `period_id` | string | ✓ | طبق فرمت INTEGRATION_CONTRACT.md بخش ۳ | دوره این مقدار — معمولاً از header فرم خوانده می‌شود |
| `data_source` | string | اختیاری | — | منبع داده (سیستم داخلی، محاسبه دستی، ...) |
| `note` | string (max 500) | اختیاری | — | توضیح کوتاه اگر مقدار غیرعادی است؛ **نباید اطلاعات کمی در آن باشد** |

**تعداد ردیف‌ها:** محدوده پیشنهادی ۳ تا ۲۰ شاخص در هر دوره. تعداد دقیق TBD پس از تصویب فهرست شاخص‌ها (در `METRIC_LAYER.md`).

### اعتبارسنجی‌های خودکار دروازه کیفیت (بخش ۴.۶ سند اجرایی)

| دروازه | بررسی | واکنش |
|---|---|---|
| کامل بودن | همه شاخص‌های اجباری واحد مقدار دارند | برگشت به واحد، ثبت دلیل |
| سازگاری ابعاد | `unit_of_measure` با تعریف شاخص می‌خواند | خطای اعتبارسنجی |
| انحراف زمانی | تغییر `value_actual` نسبت به همان دوره سال قبل بیش از ۵۰٪ نیست | هشدار — نه خطا؛ نیازمند تأیید |
| مقدار غیرمنفی | اگر `dim_indicator.allow_negative = false`، مقدار منفی رد می‌شود | خطای اعتبارسنجی |

## بخش ۲ — وضعیت پروژه‌ها و اقدامات

هر ردیف یک پروژه یا اقدام در حال اجرا است که به این واحد تخصیص دارد.

### فیلدهای هر ردیف پروژه

| نام فیلد | نوع داده | الزامی | اعتبارسنجی | توضیح |
|---|---|---|---|---|
| `project_id` | string | ✓ | باید در `dim_project` ثبت باشد | شناسه پروژه/اقدام |
| `progress_pct` | integer (0–100) | ✓ | ۰ تا ۱۰۰ | درصد پیشرفت تجمیعی |
| `status` | enum | ✓ | یکی از مقادیر جدول زیر | وضعیت در این دوره |
| `milestone_reached` | string (max 300) | اختیاری | — | آخرین دستاورد قابل تحویل رسیده‌شده |
| `next_milestone` | string (max 300) | اختیاری | — | دستاورد قابل تحویل بعدی |
| `projected_completion` | date | اختیاری | باید بعد از تاریخ گزارش باشد | تاریخ تکمیل پیش‌بینی‌شده |

### مقادیر مجاز `status`

| مقدار | معنی |
|---|---|
| `on_track` | طبق برنامه |
| `at_risk` | در خطر تأخیر — نیاز به توجه |
| `delayed` | تأخیر رسمی — تاریخ جدید لازم است |
| `completed` | تکمیل‌شده در این دوره |
| `suspended` | متوقف‌شده — دلیل در بخش ۳ موانع |
| `not_started` | آغاز نشده — فقط اگر در برنامه این دوره بوده |

## بخش ۴ — روایت و تحلیل واحد

این بخش تنها بخش متن آزاد فرم است. محتوا مستقیماً به **محصول A (مغز دوم)** می‌رود.

### فیلدهای بخش ۴

| نام فیلد | نوع داده | الزامی | راهنمای تکمیل |
|---|---|---|---|
| `narrative_summary` | text (max 3000) | ✓ | روایت کلی دوره: مهم‌ترین اتفاق، تغییر فضا، دستاورد شاخص |
| `context_notes` | text (max 2000) | اختیاری | اطلاعات زمینه‌ای که در شاخص‌ها نمی‌آید (تغییر قانون محلی، رویداد مؤثر بیرونی) |
| `lessons_learned` | text (max 1000) | اختیاری | آموخته‌هایی که ارزش ثبت دارند برای دوره‌های آینده |

**راهنمای نویسندگی برای واحدها:**
- از نوشتن اعداد در این بخش بپرهیزید؛ آنها در بخش ۱ ثبت شده‌اند.
- این بخش «چرا» است، نه «چه»؛ «چه» در بخش‌های ۱ و ۲ هست.
- کوتاه‌نویسی ارجح است بر جامع‌نویسی.

## بخش ۵ — پیوست‌ها

### فیلدهای هر پیوست

| نام فیلد | نوع داده | الزامی | محدودیت |
|---|---|---|---|
| `file` | binary | — | حداکثر ۲۵ مگابایت در هر فایل |
| `file_type` | enum | ✓ | `pdf` / `xlsx` / `docx` / `jpg` / `png` / `other` |
| `description` | string (max 300) | ✓ | عنوان/توضیح پیوست |
| `classification` | enum | ✓ | سطح محرمانگی پیوست، مستقل از خود فرم |

**فرمت‌های مجاز:** PDF (ترجیح‌داده‌شده)، Excel، Word، تصویر. فایل‌های اجرایی (.exe, .zip, .rar) پذیرفته نمی‌شوند.

**مسیر پردازش پیوست:**
```
فایل آپلودشده
     ↓
Object Storage (رمزگذاری‌شده)
     ↓
n8n ingestion workflow محصول A
     ↓
Text extraction + chunking
     ↓
Qdrant embedding
     ↓
پیوند bridge_report_document در انبار داده B
```

## گردش کار تأیید (Approval Workflow)

```
draft
  ↓ ارسال توسط واحد
submitted
  ↓ بررسی توسط معاونت برنامه‌ریزی یا دفتر مربوطه
under_review
  ↓ تأیید                    ↓ رد با دلیل
approved                   rejected (→ واحد اصلاح می‌کند → submitted)
```

پس از تأیید، رکورد در لایه `validated` قفل می‌شود و هیچ تغییری بدون ثبت اصلاحیه (`is_amendment = true`) مجاز نیست.
