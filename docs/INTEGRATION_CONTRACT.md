# INTEGRATION_CONTRACT.md — قرارداد یکپارچگی محصول A و B

> **هدف این فایل:** مهم‌ترین سند فنی پلتفرم. واژگان مشترک اجباری، طرح شناسه‌گذاری، تقویم دوره‌ها، JSON Schema بلوک متادیتا، جهت جریان داده بین دو محصول، و قواعد نسخه‌بندی قرارداد. باید قبل از خط اول کد محصول B نهایی شود.

## وضعیت
محتوای WP-2. مبنا: بخش ۳ سند اجرایی (`PLATFORM.md`). بخش‌های علامت‌خورده با «**[پیشنهادی — نیازمند تأیید]**» طرح این مخزن‌اند و هنوز تصمیم مصوب سازمانی نیستند.

## ۱. واژگان مشترک اجباری

هر رکورد در هر دو محصول — چه ردیف جدول در محصول B، چه Note در محصول A — باید این کلیدها را داشته باشد:

| کلید | نوع | توضیح |
|---|---|---|
| `entity_id` | string | شناسه یکتای سراسری (بخش ۲) |
| `unit_id` | string | واحد سازمانی مسئول — نال‌پذیر فقط برای موجودیت‌های بیرون از سلسله‌مراتب واحدها (مثل `Country`) |
| `period_id` | string | دوره زمانی استاندارد (بخش ۳) — اجباری برای هر رکورد عملیاتی/دوره‌ای |
| `issue_id` | string، اختیاری | ارجاع به موجودیت `Issue` در صورت وجود |
| `classification` | enum | سطح محرمانگی (بخش ۵) |
| `provenance` | object | منبع، زمان ورود، عامل ورود (بخش ۵) |

قاعده: نبود `unit_id` یا `period_id` روی رکوردی که باید داشته باشد، خطای اعتبارسنجی است، نه مقدار پیش‌فرض خالی.

## ۲. طرح شناسه‌گذاری (ID Scheme)

### ۲.۱ قاعده کلی

```
{PREFIX}-{SCOPE}-{SEQUENCE}
```

- `PREFIX` — نوع موجودیت، ۲ تا ۴ حرف بزرگ لاتین.
- `SCOPE` — کد دامنه (کد کشور ISO 3166-1 alpha-2، یا کد واحد سازمانی، بسته به نوع موجودیت).
- `SEQUENCE` — عدد ترتیبی ۴ رقمی، صفر-پد شده، **یکتا در محدوده `PREFIX-SCOPE`** (نه سراسری).

### ۲.۲ جدول پیشوندها

| PREFIX | موجودیت | SCOPE | مثال |
|---|---|---|---|
| `ORG` | Organization (بیرونی) | کد کشور | `ORG-TR-0042` |
| `CTY` | Country | کد کشور خودش | `CTY-TR-0001` |
| `UNT` | Unit (واحد سازمانی داخلی) | کد واحد مادر یا `HQ` | `UNT-HQ-0003` |
| `REP` | نمایندگی/رایزنی | کد کشور | `REP-TR-0001` |
| `PRS` | Person | کد کشور یا `HQ` | `PRS-TR-0017` |
| `IND` | Indicator (تعریف شاخص) | `HQ` (شاخص‌ها سراسری‌اند) | `IND-HQ-0014` |
| `PRJ` | Project/Program | کد واحد مالک | `PRJ-UNT03-0006` |
| `ISS` | Issue | `HQ` | `ISS-HQ-0021` |
| `DEC` | Decision | `HQ` | `DEC-HQ-0009` |
| `RES` | Resolution | `HQ` | `RES-HQ-0002` |
| `DIR` | Directive | `HQ` | `DIR-HQ-0004` |
| `RPT` | Report submission | کد واحد | `RPT-UNT03-0128` |
| `SIG` | Signal | کد کشور | `SIG-TR-0055` |
| `INS` | Insight | کد کشور یا `HQ` | `INS-TR-0012` |

**[پیشنهادی — نیازمند تأیید]** این جدول کامل نیست؛ با افزودن موجودیت جدید یک ردیف به همین جدول اضافه می‌شود، نه یک طرح موازی.

### ۲.۳ قاعده تخصیص شماره ترتیبی

- شماره ترتیبی توسط **Entity Registry** (هسته مشترک) صادر می‌شود، نه توسط محصول A یا B مستقیماً — تا از تصادم جلوگیری شود.
- تخصیص **atomic** و **append-only** است: شماره حذف‌شده دوباره صادر نمی‌شود.
- محصول B هنگام Ingestion از BPMS، اگر رکورد BPMS شناسه داخلی خودش را دارد (مثل شماره کارتابل)، آن را در `provenance.source_ref` نگه می‌دارد، نه به‌جای `entity_id`.

### ۲.۴ Entity Resolution و Alias

طبق بخش ۲۹ سند محصول A، یک موجودیت واحد می‌تواند چند نام ظاهری داشته باشد (مثال: «Yunus Emre Institute» / «YEE» / «موسسه یونس امره»). این‌ها باید به یک `entity_id` واحد نگاشت شوند؛ جدول Alias جزئی از Entity Registry است، نه از این قرارداد. این سند فقط تضمین می‌کند که یک‌بار `entity_id` صادر شد، همان در هر دو محصول استفاده می‌شود.

## ۳. تقویم دوره‌ها (`period_id`)

### ۳.۱ فرمت

```
{YEAR}-{GRAIN}[{INDEX}]
```

| Grain | فرمت | مثال شمسی | معادل میلادی مثال |
|---|---|---|---|
| سال | `{YYYY}` | `1405` | `2026-2027` (سال شمسی روی دو سال میلادی می‌افتد) |
| فصل | `{YYYY}-Q{1-4}` | `1405-Q1` | تقریباً ۲۱ مارس تا ۲۱ ژوئن ۲۰۲۶ |
| ماه | `{YYYY}-M{01-12}` | `1405-M01` | فروردین ۱۴۰۵ ≈ ۲۱ مارس تا ۲۰ آوریل ۲۰۲۶ |

- سال پایه، سال شمسی است — چون گزارش‌دهی واحدها و بودجه سازمانی روی تقویم شمسی می‌چرخد.
- `YEAR` همیشه ۴ رقمی شمسی است (`1405`، نه `05` یا `1405-1406`).

### ۳.۲ نگاشت به میلادی

هر `period_id` باید در Entity Registry به یک بازه دقیق میلادی (`start_date`, `end_date`, هر دو ISO-8601) نگاشت شود. این نگاشت **یک‌بار در جدول `dim_period`** (بخش ۴.۴ سند اجرایی) نگهداری می‌شود؛ هیچ سرویسی مجاز به محاسبه دستی تبدیل شمسی↔میلادی در کد پراکنده نیست.

**[پیشنهادی — نیازمند تأیید]** مرز شروع فصل/سال شمسی (اعتدال بهاری) باید توسط کتابخانه تقویم استاندارد محاسبه شود، نه فرمول تقریبی؛ کتابخانه پیشنهادی در `SETUP.md` (WP-8) مشخص می‌شود.

### ۳.۳ قاعده تطبیق دوره بین دو محصول

محصول B دوره گزارش‌دهی واحدها را عمدتاً به‌صورت فصلی یا ماهانه دارد (TBD — سؤال بی‌پاسخ #2 در `ASSUMPTIONS.md`). محصول A اسناد را با تاریخ دقیق ثبت می‌کند و در لحظه بازیابی به `period_id` نگاشت می‌دهد. یعنی: **`period_id` استاندارد سراسری است، اما واحد تولید محتوا در سطح ریزتری (روز) کار می‌کند و در سطح `period_id` تجمیع می‌شود.**

## ۴. سطح‌بندی محرمانگی (`classification`)

```
public | internal | restricted | confidential
```

| مقدار | معنی | دسترسی |
|---|---|---|
| `public` | منابع باز (اخبار، وب) | بدون محدودیت داخلی |
| `internal` | اسناد عادی سازمانی | همه کاربران احرازشده |
| `restricted` | گزارش حساس واحد/نمایندگی | نقش‌های تعریف‌شده + مالک واحد |
| `confidential` | مصوبات/دستورات حساس، پرونده ویژه | فهرست صریح کاربر، بدون توارث نقش |

**[پیشنهادی — نیازمند تأیید]** بالاترین سطحی که وارد سیستم می‌شود هنوز نامعلوم است (سؤال #4 در `ASSUMPTIONS.md`)؛ این جدول فرض می‌گیرد بالاترین سطح `confidential` است و مدل ابری برای آن ممنوع است (طبق بخش ۸ سند اجرایی).

## ۵. ساختار `provenance`

```yaml
provenance:
  source_system: string      # مثال: "bpms", "obsidian-manual", "web-clipper", "n8n-ingestion"
  source_ref: string         # شناسه داخلی سیستم مبدأ (مثال: شماره کارتابل BPMS)
  ingested_at: string        # ISO-8601 timestamp
  ingested_by: string        # user_id یا نام workflow
  ingestion_method: enum     # manual | automated | api
```

## ۶. JSON Schema — بلوک متادیتای مشترک

فایل مرجع ماشین‌خوان: [`schemas/common-metadata.schema.json`](./schemas/common-metadata.schema.json)

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://platform.internal/schemas/common-metadata.schema.json",
  "title": "Common Metadata Block",
  "type": "object",
  "required": ["entity_id", "period_id", "classification", "provenance"],
  "properties": {
    "entity_id": {
      "type": "string",
      "pattern": "^[A-Z]{2,4}-[A-Z0-9]+-[0-9]{4}$",
      "description": "شناسه یکتای سراسری طبق بخش ۲"
    },
    "unit_id": {
      "type": ["string", "null"],
      "pattern": "^UNT-[A-Z0-9]+-[0-9]{4}$"
    },
    "period_id": {
      "type": "string",
      "pattern": "^[0-9]{4}(-Q[1-4]|-M(0[1-9]|1[0-2]))?$",
      "description": "طبق بخش ۳ — سال، فصل یا ماه شمسی"
    },
    "issue_id": {
      "type": ["string", "null"],
      "pattern": "^ISS-[A-Z0-9]+-[0-9]{4}$"
    },
    "classification": {
      "type": "string",
      "enum": ["public", "internal", "restricted", "confidential"]
    },
    "provenance": {
      "type": "object",
      "required": ["source_system", "ingested_at", "ingestion_method"],
      "properties": {
        "source_system": { "type": "string" },
        "source_ref": { "type": ["string", "null"] },
        "ingested_at": { "type": "string", "format": "date-time" },
        "ingested_by": { "type": ["string", "null"] },
        "ingestion_method": {
          "type": "string",
          "enum": ["manual", "automated", "api"]
        }
      }
    }
  }
}
```

## ۷. جهت جریان داده

```
محصول B  ──────────────►  محصول A
  متن روایی گزارش‌ها
  مصوبات و دستورات
  شرح موانع و ریسک‌ها
  صورت‌جلسات
  (به‌عنوان سند دانشی وارد حافظه سازمانی می‌شوند)

محصول A  ──────────────►  محصول B
  پنل شواهد کنار هر عدد
  سوابق و تصمیم‌های مشابه
  تحلیل علت انحراف با ارجاع
  تبدیل سیگنال بیرونی به مسئله
```

هیچ سرویسی مجاز نیست مستقیماً به پایگاه‌داده محصول دیگر Query بزند؛ تبادل فقط از طریق API رسمی هر محصول (بخش ۹ — خارج از دامنه این اسپرینت، تعریف API بعداً).

## ۸. سه قانون تخطی‌ناپذیر

1. **عدد فقط از B می‌آید.** محصول A هرگز عدد گزارش نمی‌کند؛ اگر لازم شد، عدد را از API محصول B می‌خواند و بازنشر می‌کند.
2. **روایت فقط از A می‌آید.** محصول B تحلیل متنی خودش را نمی‌سازد؛ از سرویس تحلیل مغز دوم استفاده می‌کند.
3. **موجودیت `Issue` نقطه اتصال رسمی است.** یک انحراف در B و یک سیگنال در A، هر دو می‌توانند به یک `Issue` تبدیل شوند و از آن به بعد یک پرونده واحد دارند.

## ۹. قواعد نسخه‌بندی قرارداد

### ۹.۱ شماره‌گذاری

این قرارداد نسخه‌بندی semver غیر-نرم‌افزاری دارد: `MAJOR.MINOR`.

- **MINOR** (`1.0` → `1.1`): افزودن فیلد اختیاری جدید، افزودن مقدار جدید به یک enum (بدون حذف قدیمی‌ها)، افزودن پیشوند جدید به جدول شناسه‌گذاری. **Backward-compatible.**
- **MAJOR** (`1.x` → `2.0`): تغییر فرمت `entity_id` یا `period_id`، حذف/تغییر معنای فیلد اجباری، تغییر enum به‌گونه‌ای که مقدار قدیمی نامعتبر شود. **Breaking change.**

### ۹.۲ رویه اعلام تغییر شکسته

1. تغییر پیشنهادی ابتدا به‌صورت ADR در `decisions/` ثبت می‌شود (وضعیت: پیشنهادی).
2. تغییر باید توسط مالک هر دو محصول (Product Owner محصول A و B) تأیید شود — چون قرارداد مشترک است.
3. نسخه جدید قرارداد با یک migration note منتشر می‌شود: چه چیزی می‌شکند، مسیر مهاجرت داده موجود چیست.
4. تا پایان دوره مهلت مهاجرت (**[پیشنهادی — نیازمند تأیید]** پیشنهاد: حداقل یک چرخه انتشار محصول B، یعنی یک ماه)، هر دو نسخه هم‌زمان پذیرفته می‌شوند.
5. ADR وضعیت «پذیرفته‌شده» می‌گیرد و شماره نسخه در بالای همین فایل به‌روز می‌شود.
